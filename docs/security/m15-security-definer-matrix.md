# M15 SECURITY DEFINER / RPC Exposure Matrix

Generated by direct query against `pg_proc`/`has_function_privilege` on the
real local database (authoritative — not migration-file parsing, which
undercounted earlier in this audit: 27 was wrong, the true count is **40**).

```sql
select p.proname, n.nspname, p.prosecdef,
  case p.prorettype::regtype::text when 'trigger' then true else false end as is_trigger,
  has_function_privilege('anon', p.oid, 'execute') as anon_execute,
  has_function_privilege('authenticated', p.oid, 'execute') as authenticated_execute,
  has_function_privilege('service_role', p.oid, 'execute') as service_role_execute,
  p.proconfig
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname in ('public','private') and p.prosecdef = true
order by n.nspname, is_trigger, p.proname;
```

No secrets or customer data were printed while auditing — every check below
is a privilege/shape check (`has_function_privilege`, return type, grant
tables), never a data read.

## Regression guardrail (permanent, catches future RPCs automatically)

The four P0s found this session (three in this pass, one earlier) share
one root cause: `grant execute ... to service_role` without the paired
`revoke execute ... from public, anon, authenticated, service_role` —
Postgres's default PUBLIC EXECUTE grant on function creation silently
stays in effect for `anon`/`authenticated` too. This is a systemic
pattern, not four isolated bugs, so the fix is a permanent regression
test, not just four migrations:

- **`supabase/tests/database/019_security_definer_privilege_invariant.test.sql`**
  queries `pg_proc`/`has_function_privilege` directly (not a hard-coded
  function-name list) and fails if ANY non-trigger SECURITY DEFINER
  function in `public` is executable by `anon`/`authenticated` unless
  it's in the tiny, explicit, reviewed allowlist below. This catches every
  function that exists today **and every one added in the future** — no
  migration-review discipline required to catch the next instance of this
  bug class, because Postgres's own catalog is the source of truth the
  test reads. Verified this actually works (not just passes by
  coincidence): temporarily re-granting `authenticated` execute on
  `claim_next_transcription_job` inside a throwaway `begin;...rollback;`
  transaction made the guardrail query immediately flag it — see the
  verification note in that test file's own header.
- The same file also asserts the allowlist stays at exactly 4 entries (no
  silent growth) and that every known service-role-only RPC still has
  service_role access (the _other_ direction of the same class of
  mistake — a future migration could revoke without re-granting).
- **`supabase/tests/database/018_side_effect_denial.test.sql`** goes one
  level deeper than "the call errors": using real fixture rows, it proves
  a denied call causes **zero state mutation** (not just an exception) for
  all 4 P0-fixed functions plus `claim_next_meeting_intelligence_run`,
  including a positive control proving the same fixtures DO change state
  when the intended caller (`service_role`) performs the equivalent call —
  so the "unchanged" assertions aren't tautologies against fixtures that
  could never change.

**Migration rule going forward**: every future `SECURITY DEFINER`
function migration must explicitly, in this order:

1. `revoke execute on function ... from public, anon, authenticated, service_role;`
2. `grant execute on function ... to <only the intended caller role(s)>;`

Never rely on the Postgres default (which grants EXECUTE to PUBLIC on
function creation). If the intended caller is `authenticated`, the
function must also do its own real internal authorization (see the
`confirm_customer_truth_fact` family below for the pattern:
`organization_id = private.current_organization_id()` row-scoping plus a
`private.assert_*_authorized(...)` ownership check) — a broad
`authenticated` grant is only safe when the function enforces its own
boundary. If a new function is genuinely meant to be
`authenticated`-callable, add it to `019`'s allowlist in the same PR that
adds the function, along with its own dedicated authorization test
(mirroring `012_customer_truth_actions.test.sql`) — the guardrail test
will otherwise correctly fail and block the PR, which is the point.

## Category A — Trigger functions (20)

SECURITY DEFINER: yes, on all 20. PostgREST exposure: **NO** for all —
Postgres structurally refuses to invoke a `returns trigger` function
outside real trigger context (`ERROR: trigger functions can only be
called as triggers`), regardless of EXECUTE grants. The catalog shows
`anon`/`authenticated`/`service_role` all `true` for these — that is
**expected and harmless**, not a finding, because the call path itself is
blocked at the language level before any grant is even consulted.
`search_path`: all 20 set `search_path=public` explicitly (safe — no
search_path-hijack surface). Intended caller: Postgres trigger machinery
only. Org boundary enforcement: this IS their purpose for the
`validate_*_org_consistency` ones (reject a row whose FK'd parent belongs
to a different org) and the `prevent_transcript_evidence_*` /
`validate_*_evidence_segments` ones (reject a segment id from a different
meeting/already-completed transcript). Regression coverage: exercised
indirectly by every existing INSERT/UPDATE/DELETE test on their tables
(004/007/008/009/010/011/012/013) — not called directly, never need to
be.

## Category B — `private` schema helpers (9)

SECURITY DEFINER: yes, on all 9. PostgREST exposure: **NO** — `private` is
not in `supabase/config.toml`'s `api.schemas` (`["public",
"graphql_public"]`), so no REST/RPC endpoint can reach these regardless of
grant. The catalog shows broad `anon`/`authenticated`/`service_role`
EXECUTE on all 9 — this is **intentional, not a gap**: these are called
_from inside_ RLS policy expressions and other SECURITY DEFINER function
bodies, which run as whatever role issued the original query, so they
must be broadly executable to do their job. `search_path`: all 9 set
`search_path=public` (safe). Intended caller: internal SQL only (RLS
policies, other functions), never a direct API caller. These functions
themselves ARE the org-boundary/authorization primitives everything else
in this matrix is built on:

| Function                                                | Purpose                                                                                |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `current_profile_id`                                    | resolves `auth.uid()` → `profiles.id`                                                  |
| `current_membership_id`                                 | resolves caller → their active `organization_memberships.id`                           |
| `current_organization_id`                               | resolves caller → their `organization_id` (the actual multi-tenant boundary primitive) |
| `current_role_key`                                      | resolves caller → their role key                                                       |
| `is_org_admin`                                          | boolean: is caller an admin in their org                                               |
| `has_permission(key)`                                   | boolean: does caller's role carry a given permission                                   |
| `is_manager_of(membership_id)`                          | boolean: is caller a manager-in-tree of the given membership                           |
| `assert_call_record_authorized(owner_membership_id)`    | raises unless caller owns the record or is admin/in-scope manager                      |
| `assert_customer_truth_authorized(owner_membership_id)` | same, for customer-truth facts                                                         |

Regression coverage: 001 (RLS), 002 (hierarchy), 005 (`is_manager_of`
dedicated file), and transitively every policy test in 001–014 (every
`create policy` in this schema calls one of these).

## Category C — Real (non-trigger) `public` functions (11)

These are the ones that matter: real return types, genuinely callable
over PostgREST if the grant allows it. Full detail per function:

### `claim_next_calendar_event_job()`

- Intended caller: internal calendar-sync queue worker (service_role only)
- Grants: `anon=false, authenticated=false, service_role=true` ✅ **correct now**
- **P0 (found earlier this session, fixed in `20260911150001`)**: originally only `grant ... to service_role` with no revoke — PUBLIC's default grant meant `anon`/`authenticated` could dequeue/claim any org's job. Confirmed exploitable, confirmed fixed.
- Explicit caller auth inside function: none — the grant IS the boundary (correct for a pure internal queue-claim with no caller identity concept)
- Org boundary: N/A by design (claims oldest job across ALL orgs — that's the worker's job)
- search_path: safe (`search_path=public`)
- PostgREST exposure: yes, structurally — now blocked by grant
- Regression: `015_security_hardening.test.sql` (3 assertions); side-effect-denial + guardrail: `018`, `019`

### `claim_next_transcription_job()`

- Intended caller: internal transcription queue worker (service_role only)
- Grants: `anon=false, authenticated=false, service_role=true` ✅ **correct now**
- **P0 (found + fixed this session, `20260911150002`)**: same gap as above — confirmed exploitable (`select * from public.claim_next_transcription_job()` succeeded as both `anon` and `authenticated` before the fix), confirmed fixed.
- Explicit caller auth: none (same reasoning as above — correct)
- Org boundary: N/A by design
- search_path: safe
- Regression: `017_more_queue_claim_hardening.test.sql`; side-effect-denial + guardrail: `018`, `019`

### `claim_scheduler_call_meeting(uuid,uuid,uuid,uuid,call_type)`

- Intended caller: internal scheduler-linkage reconciliation worker (service_role only)
- Grants: `anon=false, authenticated=false, service_role=true` ✅ **correct now**
- **P0 (found + fixed this session, `20260911150002`)** — the most concerning of the three "queue" P0s: takes `p_scheduler_call_id, p_organization_id, p_meeting_id, p_customer_id, p_call_type` as **entirely caller-supplied arguments with zero internal authorization check of its own**. Before the fix, any `anon`/`authenticated` caller could link an arbitrary scheduler call to an arbitrary meeting in ANY organization, bypassing both tables' RLS entirely. Confirmed via `has_function_privilege` = true for both roles before the fix; confirmed false after.
- Explicit caller auth inside function: **none** — this function was never meant to have any; the grant was its only boundary, which is why the missing revoke was so serious
- Org boundary: the UPDATE `where` clauses filter by `organization_id = p_organization_id`, but that argument is caller-supplied — org boundary only holds now that the grant restricts callers to service_role (a trusted internal caller that supplies real ids)
- search_path: safe
- Regression: `017_more_queue_claim_hardening.test.sql`; side-effect-denial + guardrail: `018` (proves a denied call links NEITHER the scheduler call NOR the meeting), `019`

### `complete_transcription_job(uuid,uuid,text,text,boolean,jsonb,jsonb,numeric,numeric,jsonb)`

- Intended caller: internal transcription worker, after a provider call completes (service_role only)
- Grants: `anon=false, authenticated=false, service_role=true` ✅ **correct now**
- **P0 (found + fixed this session, `20260911150003`)** — the highest-impact of the four P0s found: `p_segments` is raw, caller-supplied `jsonb` inserted directly as new `transcript_segments` rows, and `p_transcript_id`/`p_organization_id` are also caller-supplied. Before the fix, any `anon`/`authenticated` caller could inject **arbitrary fabricated transcript content** into any organization's transcript and mark it `completed` — a genuine cross-tenant data-integrity/injection vulnerability, not just an unauthorized-read/claim. Confirmed exploitable (privilege check `true` for both roles) before the fix; confirmed denied after.
- Explicit caller auth: none (grant was the only boundary — same class of gap as above)
- Org boundary: `where id = p_transcript_id and organization_id = p_organization_id` — again, only trustworthy because the caller is now restricted to service_role
- search_path: safe
- Regression: `017_more_queue_claim_hardening.test.sql`; side-effect-denial + guardrail: `018` (proves a denied call attempting a real attacker-authored "FABRICATED BY ATTACKER" segment leaves the transcript `processing` and the one real pre-existing segment byte-for-byte unchanged), `019`

### `confirm_customer_truth_fact(uuid)`

- Intended caller: any authenticated AM/manager/admin who owns or manages the fact's customer
- Grants: `anon=false, authenticated=true, service_role=false` ✅ **correct** (this one is MEANT to be authenticated-callable — the authorization is inside the function, not the grant)
- Explicit caller auth inside function: **yes, real** — looks up the fact scoped to `organization_id = private.current_organization_id()` (own-org only), then calls `private.assert_customer_truth_authorized(owner_membership_id)` (raises unless caller owns the customer or is admin/in-scope manager), then guards the status transition and does a CAS-guarded UPDATE (raises on concurrent modification)
- Org boundary: enforced via `current_organization_id()` in the lookup — a cross-org fact id simply isn't found
- search_path: safe
- Regression: `012_customer_truth_actions.test.sql` (part of 16 `throws_ok` assertions in that file)

## Exploit-testing contamination check

Before adding fixture-based tests, the live local database was checked
for any row created by this session's earlier exploit-verification
commands (which ran actual privileged calls, not just privilege checks,
against `claim_next_transcription_job` and `claim_scheduler_call_meeting`
before their fixes landed). Searched for the exact fake UUIDs used during
that testing (`00000000-0000-0000-0000-000000000001`) across
`scheduler_calls`, `meetings`, `meeting_transcripts`,
`transcript_segments`, `calendar_event_jobs`, and `ai_runs` — zero rows
matched. The only rows matching a broader `00000000-0000-0000-0000-%`
organization-id pattern were confirmed to be this session's own
legitimate, intentional demo-seed data (`supabase/seed.sql`'s "Organization
A (Test)" fixture plus the Priya Shah demo customer/meeting/transcript
seeded for the M12/M13 human-test walkthrough), not exploit artifacts. No
transcript content or customer PII is reproduced in this report.
