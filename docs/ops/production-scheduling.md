# Production Scheduling (M17B)

Concrete implementation of the scheduling topology `docs/ops/production-environment.md` §11 analyzed and recommended (hybrid: scheduled HTTP for six job types, one dedicated worker for transcription). The actual cron configuration lives in `vercel.json` at the repo root — this document is the human-readable reference for what each entry does, not a duplicate source of truth for the cadence numbers themselves.

## How the scheduled-HTTP path is authorized

Every `/api/internal/*` route now accepts two independent credentials, checked by the shared helper `apps/web/lib/internal-route-auth.ts`:
- `x-internal-queue-secret` header (`INTERNAL_QUEUE_SECRET`) — the original mechanism, unchanged, still works for manual/on-demand `curl` invocation exactly as it always has.
- `Authorization: Bearer <CRON_SECRET>` — the shape Vercel Cron Jobs send natively (Vercel automatically attaches this header, reading its value from the project's own `CRON_SECRET` environment variable, when one is configured — this is Vercel's own documented convention, not something this app invented a custom protocol for).

Each route now exports `GET` (aliased to the same handler as `POST`) so Vercel's cron invocation — always a GET — reaches the same code path manual `POST` calls already use. **Deliberate exception: `/api/internal/transcription/process` has no `GET` export** — see below.

## Why transcription is the one exception

`packages/domain/src/audio-transcode.ts` shells out to the system `ffmpeg`/`ffprobe` binaries unconditionally for every transcription job (`transcription.ts:216`). A bare serverless function doesn't provide these. `workers/transcription-worker/Dockerfile` installs them the same way CI already proves sufficient (`apt-get install ffmpeg`) — verified for real during this checkpoint: built the image, confirmed both binaries present and runnable inside it (`ffmpeg -version`/`ffprobe -version`), and ran the actual worker script inside the container end-to-end (module resolution succeeds, environment loading succeeds, the tick loop starts, a simulated network failure is caught by the existing try/catch without crashing the process).

## A real bug found and fixed while building this: `node` cannot run either worker script

Both `workers/orchestrator/bot-worker.mjs` (pre-existing, M6) and the new `workers/transcription-worker/transcription-worker.mjs` import `@applywizz/domain/*`, whose own internal files use extensionless relative imports (e.g. `transcription.ts` importing `./audio-transcode`, no `.ts` suffix). Node's native ESM loader does not resolve these to `.ts` — running either script with plain `node` throws `ERR_MODULE_NOT_FOUND` immediately. **Confirmed by actually running `bot-worker.mjs` this way** — it has never worked via the exact command its own header comment has documented since M6. Both workers' `package.json` scripts, header comments, and (for the new worker) the Dockerfile `CMD` now use `tsx` (already a repo devDependency) instead of bare `node` — confirmed fixed by running both scripts again afterward and watching them get past module resolution to the expected "missing env var" failure.

## What Vercel Cron itself provides, not rebuilt here

"Are scheduled jobs ticking?" (§8's first health question, beyond web/worker liveness) is directly answered by the hosting platform's own cron execution history/dashboard once deployed — Vercel Cron Jobs log every invocation and its result natively. This checkpoint does not duplicate that into a new in-app view; building a second, parallel "did the cron actually fire" tracker would be exactly the kind of infrastructure §8 says not to add ("do not build a large new observability product... keep it operational and minimal"). If the chosen platform ends up being something other than Vercel, this is the one part of this document that would need a different answer — the per-job cadence/retry/alert table above doesn't change either way.

## Known limitation: a fully-dead worker can't report its own death

The Docker `HEALTHCHECK` and container-orchestrator restart policy are the correct layer for "is the transcription worker process alive" — a process that has crashed entirely cannot write an incident about its own crash. If the worker is down long enough for a job it had claimed to go stale, M16's existing stuck-job detection (`/admin/operations`) surfaces that downstream effect, which is the honest, available signal — not a direct "worker is down" alert. This is a structural property of the design, not something this checkpoint can close without external monitoring on the container itself (out of scope — no such monitoring infrastructure exists to wire into yet).
